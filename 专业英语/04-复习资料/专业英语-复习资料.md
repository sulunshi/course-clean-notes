# 专业英语｜复习资料

按实际课程日期排列；后续课程继续补充在本文件中。

## 2026-09-17｜第二周

### 第一节课

#### 课程定位

- 面向软件工程专业研究生，训练专业场景中的听、说、读、写能力。
- 学习目的不只是完成课程，还包括阅读英文技术资料、写论文和文档、参加国际会议、完成英文问答与团队协作。
- 第一手技术资料、编程文档和开源社区交流大量使用英文。

#### 课程能力目标

- 掌握软件工程核心术语和技术英语的构词、句式与语言特征。
- 阅读技术文档、学术论文和前沿报告，并形成批判性阅读能力。
- 进行课堂发言、专业展示、会议问答和跨文化沟通。
- 撰写学术文章、技术文章、专业邮件、需求文档、设计文档和用户手册。
- 使用 AI 辅助学习时保持判断力，不让 AI 替代自己的思考和表达。

#### 考核与作业

- 以过程性考核为主，没有期末闭卷考试。
- 原始转写可辨认出的项目包括平时表现约 10%、专业阅读约 20%、演讲或展示约 25%、技术写作约 25%；最终比例应以老师的正式通知为准。
- 专业阅读包含同伴互评。
- 使用 AI 完成任务时需要附 AI 使用说明，解释自己如何借助 AI 提升专业英语能力。

#### 构词法重点

- 常见前缀：`re-` 表示 again/back，`de-` 表示 remove/reverse；还需关注 `pre-`、`post-`、`inter-`、`micro-`。
- 常见后缀：`-able/-ible` 表示能力或可能性，`-tion/-sion` 表示动作或过程，`-ize` 表示使之发生变化，`-ment` 表示过程或结果，`-ity` 表示性质或状态。
- 常见合成结构包括名词加名词、形容词加名词等，例如 database management、cloud computing、artificial intelligence、distributed system。

#### 软件工程术语

- API：Application Programming Interface
- SDK：Software Development Kit
- IDE：Integrated Development Environment
- CI：Continuous Integration
- CD：结合语境可能是 Continuous Delivery 或 Continuous Deployment
- SDLC：Software Development Life Cycle
- QA：Quality Assurance

#### 需求、用户故事与测试

- 功能性需求描述系统提供什么功能；非功能性需求描述 performance、security、usability、reliability 等质量属性。
- 用户故事关注角色、需求和价值，常用框架为 “As a role, I want a feature, so that I can obtain a benefit.”
- 课堂提到的测试表达包括 unit testing、integration testing、system testing 和 end-to-end testing。
- TDD 是 Test-Driven Development；BDD 是 Behavior-Driven Development。

#### 老师反复强调的学习观念

- 不要因为发音、语法不完美而不敢开口。
- 语言学习需要亲自回忆、举例和使用，不能只把问题交给 AI。
- 技术写作要清楚、简洁、正确，并考虑跨文化表达是否得体。
- “The limits of my language are the limits of my world.”

### 第二节课

#### 可确认的课堂内容

- CI/CD 流程可概括为 Code、Build、Test、Deploy、Monitor。
- 技术翻译需要先找出关键动作、对象和逻辑关系，不能只做机械的逐字翻译。
- 课堂练习方式是先自行尝试翻译，再根据老师的讲解修正表达。
- 课堂材料涉及 requirements、code review、processing time 和 “to handle” 等表达。
- 老师布置了课后提交任务，截止时间为下次课前；具体内容应以课程群通知为准。

#### 转写中出现但语境不足的术语

- dynamic
- model compression
- federated learning
- automated design

这些术语在原始转写中没有形成足够完整的句子，不宜据此推断它们之间的技术关系。

#### 复习提醒

- 能用英文顺序说出 CI/CD 的主要阶段。
- 翻译句子时先标出动词、对象和因果或条件关系，再组织中文。
- 回看课程群，确认本次提交任务的题目、格式和截止时间。

#### 技术写作的核心要求

- 避免 `pretty good`、`works fine` 等模糊表达，应说明对象、条件、指标和结果。
- 用方法、结果、数据或分析作为判断依据，减少以个人感觉为中心的表达。
- 长名词短语要先找中心词，再判断 cloud-based、microservices-based 等修饰成分与中心词的关系。

#### 段落结构

- 先提出 main idea 或 main concept，再用 key points、数据和例子支持。
- PEEL 结构：Point、Evidence、Explanation、Link。
- limitations 或 challenges 可以引出新的 problem；随后应进行分析，并提供 details 和 justification。

#### 客观表达与缓和语气

- 不推荐：I think the method is good.
- 不推荐：We believe this method works.
- 推荐：The method demonstrates effectiveness.
- 推荐：The results indicate improved performance.
- 推荐：The analysis suggests that the method works.
- 将绝对的 `definitely` 换成更谨慎的 `tends to`、`appears to`、`suggests that`，使结论与证据强度相匹配。

#### 论文各部分的任务

- Introduction：提出背景、已有研究、问题和主要贡献，可用 “Recent advances in + 研究领域” 引入背景。
- Methods：说明步骤、技术和实验配置。
- Results：用具体数据或指标呈现发现，避免笼统评价。

#### 衔接词

- 顺序：first、then
- 因果或结果：as a result、therefore
- 连接词要服务于论证逻辑，不能只作为形式上的句首标记。

#### 最需要记住的写作原则

- 清楚说明“什么对象在什么条件下产生了什么结果”。
- 每个判断都尽量让证据或分析来支撑。
- 结论的语气强度不能超过证据能支持的程度。

## 2026-09-24｜第三周

### 与上一讲的衔接

上一讲侧重技术英语的词汇、表达和写作逻辑。本讲转向**如何阅读与判断技术文档**：先根据目的选择阅读方式，再核对信息来源与证据，最后理解作者的论证结构。

### 一、三种阅读方式

| 方法 | 要解决的问题 | 课堂强调的做法 |
| --- | --- | --- |
| 略读（skimming） | 这份文档整体讲什么、哪些部分值得细读？ | 先看标题和小标题，再看引言、各部分开头和结论；留意反复出现的术语、图表、粗体等视觉线索。 |
| 扫读（scanning） | 某个具体信息在哪里？ | 先确定目标关键词，利用目录、导航和页面查找定位；找到后阅读前后文，确认没有脱离语境。 |
| 批判性阅读（critical reading） | 这条技术信息是否可信？ | 检查来源、内容质量、时效性、证据、偏见，并与其他来源交叉验证。 |

**区别**：略读求全局，扫读求定位，批判性阅读求判断。实际阅读中可以先略读，再扫读重点，最后对关键结论进行核验。

### 二、扫读练习与 AI 核验

课堂使用 REST API 文档练习查找：支持的 HTTP 方法、认证方式、错误返回格式，以及数据量或请求方面的限制。答案不仅要写出结论，还要能指出文档中的对应原文。

借助 AI 查找时，不应把回答直接当成事实。应打开 AI 给出的链接，确认页面确实存在、内容与回答一致，并尽量追溯到官方文档等第一手资料。博客、公众号或 AI 汇总可以帮助发现线索，但不应代替原始出处。

### 三、规范文档的关键词

- **必须项**：留意 `must`、`required`、`mandatory`、`shall` 等表达。课堂举例涉及功能完整性、接口一致性、安全要求和性能指标。
- **建议项**：留意 `recommended`、`optional`、`advisable` 等表达。评估时可考虑实现成本、用户体验和长期可维护性。
- 制作检查清单时，要把必须项与建议项分开，避免把推荐做法误当成硬性要求。

### 四、评估技术信息的六个维度

1. **来源**：是否来自官方文档、原始研究或标准？作者与发布机构是谁？
2. **内容质量**：术语、逻辑、数据和例子是否准确、完整？
3. **时效性**：发布日期、更新时间和对应软件版本是什么？
4. **证据支持**：是否给出可检查的测试、数据、案例或其他依据？
5. **偏见**：是否存在商业利益、技术偏好或选择性呈现？
6. **交叉验证**：其他独立来源是否支持同一结论？分歧由什么条件造成？

**课堂特别提醒**：权威来源也要看版本和适用范围；多个来源意见不同，不能只比较“谁支持的人多”，还要比较证据质量、场景和评价指标。

### 五、常见偏见表现

- **选择性引用**：只选有利于既定观点的数据，忽略相反证据。
- **双重标准**：对不同对象使用不同评价尺度。
- **带倾向性的措辞**：用明显带有情感色彩的词影响判断。
- **过度解读**：把有限案例扩大成普遍结论，或不说明结论成立的条件。

批判性阅读不等于全盘否定，而是把观点放回数据、出处、背景和适用范围中判断。

### 六、四类常见论证结构

| 结构 | 阅读时依次追问 |
| --- | --- |
| 问题—解决方案（Problem–Solution） | 问题是什么？根本原因是什么？方案是什么？效果怎样验证？ |
| 比较—对照（Comparison–Contrast） | 比较了哪些方案？评价标准是否一致？分别适用于什么场景？ |
| 因果（Cause–Effect） | 作者提出什么原因和结果？两者的联系有何证据？是否把相关误写成因果？ |
| 证据—结论（Evidence–Conclusion） | 用了哪些数据、事实或案例？解释是否合理？结论是否超过证据的支持范围？ |

课堂中的性能问题案例先列出三个瓶颈，再给出对应的解决办法及其效果，因此主要属于**问题—解决方案**结构。

### 七、不同技术声明需要什么证据

- **性能**：测试环境、方法、指标、对照基线、压力范围及限制条件。
- **可用性**：用户研究、任务完成情况、体验数据及评价方式。
- **安全性**：安全审计、漏洞修复记录、第三方评估等可核查材料。

“性能更好”“更易用”“很安全”这类表述如果缺少对象、条件和证据，就不足以支撑技术推荐。这也延续了上一讲“技术表达应准确、客观”的要求。

### 八、本讲可直接用于复习的检查顺序

1. 先写清阅读目的：是把握全局、定位信息，还是评价结论？
2. 用标题、目录和视觉线索确定文档结构。
3. 找到关键说法后，保留原文出处并检查上下文。
4. 核对日期、版本、数据、测试条件及作者立场。
5. 判断文章采用哪类论证结构，检查结论是否由证据支持。
6. 多来源冲突时，说明各自适用场景和评价标准，再作推荐。

课堂提到的多源信息整合框架，其英文名称在原始转写中不够清晰；复习时先掌握“映射信息、评价来源、比较分歧、建立联系、综合判断”这一思路，不把不确定的缩写当成确定术语。

## 2026-10-08｜第四周

### 本讲主线

上一讲训练如何阅读和判断技术资料；本讲把批判性阅读进一步用到**研究论文**，沿 IMRAD 结构检查作者提出的问题、采用的方法、获得的结果及其贡献和局限，并在课堂上开始第二次论文批注作业。

### 一、IMRAD 各部分要回答的问题

| 部分 | 核心问题 | 阅读时重点核对 |
| --- | --- | --- |
| Introduction（引言） | 为什么研究？ | 背景、问题、已有工作、研究空白和贡献声明。 |
| Methods（方法） | 怎样研究或解决？ | 方法选择、实验设计、参数、工具、评价标准和可复现性。 |
| Results（结果） | 发现了什么？ | 实验数据、改进幅度、条件及结果是否可靠。 |
| Discussion（讨论） | 结果意味着什么？ | 学术或应用价值、局限，以及后续研究方向。 |

### 二、批判性阅读引言的四个检查点

1. **背景**：是否准确？有没有夸大问题？
2. **问题陈述**：问题的内涵、范围和重要性是否清楚？它是真实存在、值得研究的问题吗？
3. **相关工作**：介绍是否准确充分？是否只选支持作者观点的研究？
4. **贡献声明**：作者说自己贡献了什么？声明与实际证据是否相称？是否有应用价值？

课堂用“只提高约 1%，却用很强的措辞描述成果”提醒大家：不要仅凭作者的概括判断改进是否显著，应核对实际数据。

### 三、方法与实验设计

- **内部效度**：查看控制变量、对照组和可能的干扰因素是否处理合理。
- **外部效度**：查看样本及实验环境是否具有代表性，结论能否推广到其他数据或场景。多个基准和数据集可以帮助检验这一点。
- **技术方法**：为什么选择该模型或方案？有无更合适的替代方案？参数、工具和评价指标是否合理？
- **可复现性**：论文是否给出足够的代码、数据与实验细节，使别人有机会重复实验？

课堂概括的三个核心追问是：**为何选这个模型、是否存在更好替代方案、实验能否复现。**

### 四、结果和论证不能只看表面

- 统计显著性不自动等于实践价值。课堂提到 p 小于 0.05 的例子，强调还要看改进幅度及应用意义。
- 注意把相关当因果、用少量且缺乏代表性的样本推普遍结论、将对方观点简化成“稻草人”、把某方案说得全坏或另一方案说得完美，以及只依赖行业报告而缺少比较分析等问题。
- 给一项研究下判断时，应指出具体数据、论证步骤和适用范围，而不是只写“有问题”或“很重要”。

### 五、贡献与局限的评价

课堂从**理论、方法、实证、实践**四个维度讨论贡献。判断贡献时，还要检查新颖性、重要性和研究严谨性。对于“首次”“全新”“突破性”等强声明，回到三件事：与已有工作的实际差异、真实改进幅度、现实应用的可能性。论文的局限也应从具体方法、数据和结果中找依据。

### 六、第二次作业要点

- 选一篇与研究方向或兴趣相关的论文；老师建议优先选 2022 年之后的会议论文、期刊论文或预印本。篇幅不少于八页，有较完整的实验内容，不选综述，并在共享表格中避开与同学重复。
- 先通读并用自己的一句话概括论文，再找作者关于新颖性、重要性和贡献的声明及其证据。
- 在 PDF 上写**至少 20 条自己撰写的具体批注**。每条要能定位到页、段、章节、图或表，并写清声明、证据、疑问、逻辑问题、局限或复现信息等内容。只画线或写“重要”不够。
- 再写约 500 字的个人分析，涉及论文值得肯定的方面、至少一个有具体依据的局限及其重要性、复现材料是否充分，以及一个想问作者的问题。转写中关于优点数量和“六种标签”完整清单不清晰，应核对课程平台上的正式模板。
- AI 可辅助查词、翻译和理解算法；**不能代写批注或个人分析**。
- 下课前先提交课堂进度，下次上课前提交最终版本；具体以课程平台通知为准。
